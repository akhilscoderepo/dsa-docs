# Lesson architecture

Everything here is enforced by `dsa-curriculum-auditor/scripts/audit_manuscripts.py` unless marked "judgment".

## Files in a chapter directory

| File | Marker on first lines | Contents |
| --- | --- | --- |
| `00-orientation.md` | `<!-- section: orientation -->` | What the chapter covers, prerequisites, how the families differ. Starts at `## Orientation`. |
| `NN-<slug>.md` | `<!-- lesson-kind: standard -->` or `combination`, then `<!-- lesson-id: permanent-slug -->` | One micro-pattern from the spec. Exactly one `##` title, equal to the spec lesson title. A combination lesson is numbered after the unlocked-combinations section (for example `91-window-frequency-state.md`). |
| `solutions/NN-<slug>.md` | `<!-- solutions-for: NN-<slug> -->` | One `#### Solution: <exercise title>` record per exercise. |
| `90-unlocked-combinations.md` | `<!-- section: unlocked-combinations -->` | Which earlier techniques now combine, or "No new teach-now combinations" with a reason. |
| `95-review.md` | `<!-- section: review -->` | Mixed recognition prompts and rebuild checks. May include quiz blocks. |
| `ids.lock` | generated by `audit_manuscripts.py --update-ids` | The permanent lesson and exercise ids released so far. Commit it. Removing or renaming an id then fails the audit (`id-removed`), because learners' saved notes are keyed to ids. |
| `review-log.md` | written by a person only | The human quality verdict per lesson. The AI never creates or edits this file. See the auditor skill. |

Manuscripts never contain an H1; the HTML builder adds the chapter title. Headings use `##` for the lesson and `###` for stage headings.

## Stages, in order

Put the marker on its own line before the stage's `###` heading.

| Marker | What it must do | Minimum prose |
| --- | --- | --- |
| `context` | A concrete scenario and the question in plain words. Show the shape of the problem. No technique names. | 60 words |
| `contributions` (combination lessons only) | Which earlier techniques are being combined and what each contributes. | 60 words |
| `naive` | The obvious solution a competent engineer would write first, as `java` code, and a sentence saying it is correct. | 30 words + code |
| `bottleneck` | A concrete run of the naive code that exposes repeated or wasted work, then its Big-O cost with a size where it fails. Must contain a `O(...)` bound. | 60 words |
| `insight` | What the naive code throws away and how to keep it. Name the technique and its vocabulary here, once, in bold. End with the property that makes the move safe (for example monotonicity). Include `<!-- names: term, term -->` listing the introduced terms; each must appear in this stage's prose and must not appear in context or naive. | 120 words |
| `variables` | What each variable means in plain language, including its boundary convention (inclusive or exclusive). | 40 words |
| `trace` | A narrative walk through one input, step by step, including the hardest step. Add a ` ```trace ` block (format below) so the HTML build gets a stepper. Do not use a table. | 100 words |
| `code` | The `java` blueprint with comments only where a decision is non-obvious, then prose on why each decision is there, the amortized or exact complexity, and the boundary behavior. | 30 words + code |
| `applicability` | Recognition cue, the invariant stated aloud (the word "invariant" must appear), the nearest false friend (say "false friend"), a case where the technique silently fails, and a Java-specific cost if one exists. | 80 words |
| `exercises` | `### Exercises` then the exercise records. See `exercise-record-format.md`. | 4 to 7 records |

Judgment: order the scenario so the naive solution feels natural, and choose the bottleneck input so the waste is visible to the eye, not just in the Big-O.

## Trace block format

````
```trace
{"cells":[1,0,1],"pointers":["left","right"],
 "steps":[{"at":{"left":0,"right":0},"vars":{"zeros":0,"best":1},"note":"Take in index 0."}]}
```
````

`cells` are the input values. Each step gives pointer positions in `at` (a window is drawn when both `left` and `right` exist), shown variables in `vars`, and a one-sentence `note`. Generate the steps by running the algorithm in a script so they cannot drift from the code. A lesson may have more than one trace block, for example a failing case and then the corrected one. Use your own input unless a classic input is the point of the lesson.

For concurrency or other multi-actor traces:

````
```trace
{"type":"schedule","lanes":["Thread A","Thread B"],"sharedLabel":"counter",
 "question":"What can counter be?","answer":"Either 2 or 1.",
 "steps":[{"lane":0,"text":"read counter -> 0","shared":0,"note":"A reads 0."}]}
```
````

## Quiz block format

````
```quiz
{"id":"sw-rev-while-if","q":"Why `while` and not `if`?","options":["...","...","..."],"answer":0,"explain":"..."}
```
````

`answer` is the zero-based index of the correct option. Give every question a permanent `id`; without one, the saved answer is keyed by position and is lost if blocks are reordered. Use quizzes in the review section for recognition and prediction, and never as a substitute for exercises.

## Combination lessons

A combination is taught in the chapter where its last prerequisite is taught. Use `lesson-kind: combination` and the `contributions` stage. Do not teach a combination whose prerequisites appear in a later chapter; the spec lists those as deferred.

## Claims in the prose

Every factual claim about what a piece of code does on a given input ("this variant returns 3 on `abba`") must be backed by an assertion in a `java run` solution block or by the script that generated the trace. Claims written from memory were wrong more than once while this chapter was being written. If a claim cannot be run, soften it or cut it.

## Chapter closing

The review section ends with a rebuild check: three techniques the reader should be able to rewrite from the invariant, and one fresh problem they have not seen. The HTML build adds the notes boxes at the end of the chapter, so do not write a notes section yourself.
