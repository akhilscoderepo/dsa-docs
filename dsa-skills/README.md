# DSA teaching toolchain (Markdown source, interactive HTML output)

Three skills that work together. Markdown manuscripts are the single source of truth. The pilot chapter (Sliding Window, Chapter 09) is complete in `experience-first-dsa-teaching/references/exemplar/09-sliding-window/` and doubles as the quality bar.

```
chapter-specs/NN-*.md  ->  experience-first-dsa-teaching  ->  manuscripts/NN-topic/*.md   (one lesson at a time)
manuscripts/           ->  dsa-curriculum-auditor (scripts)  ->  errors, or a clean bill   (+ a human review log)
manuscripts/           ->  markdown-textbook-html            ->  output/NN-topic.html
output/*.html          ->  dsa-curriculum-auditor (audit_html, jsdom smoke test, real-browser render check)
```

| Skill | What it does |
| --- | --- |
| `experience-first-dsa-teaching` | Reads the chapter spec first. Writes one lesson per run to Markdown, in fixed stages with permanent lesson and exercise ids, full exercise records, separate solution files, traces generated by running code. One voice rule set. |
| `dsa-curriculum-auditor` | Scripts that test substance, not just structure: stage and exercise completeness, spec parity, duplicate and templated text, filler, permanent ids (`ids.lock`), a human-review gate (`review-log.md`), Java compile-and-run with an honest validation stamp, HTML audit, jsdom interaction test, and a real-Chromium render check. |
| `markdown-textbook-html` | One self-contained HTML file per chapter: notes boxes, hints, hidden solutions, progress, step-through traces, quizzes, search, versioned notes export and import. PDF is the browser's Print. |

## Setup

```
pip install -r requirements.txt     # markdown-it-py (pinned)
npm ci                              # jsdom and playwright-core (pinned, lockfile included)
```

You also need a JDK (not only a JRE) for the Java check, and a Chromium binary for the render check. Scratch files go to `--workdir`, then `$DSA_WORKDIR`, then the system temp directory.

## Quick start

```
SK=dsa-skills
CH=manuscripts/09-sliding-window
# 1. author ONE lesson at a time into $CH (see the exemplar), then audit it
python3 $SK/dsa-curriculum-auditor/scripts/audit_manuscripts.py $CH --spec chapter-specs/09-sliding-window.md --draft --stamp stamp.json
# 2. when the chapter is complete, record its ids and audit without --draft
python3 $SK/dsa-curriculum-auditor/scripts/audit_manuscripts.py $CH --spec chapter-specs/09-sliding-window.md --stamp stamp.json --update-ids
# 3. a person writes $CH/review-log.md (Reviewed-by, Date, one "- lesson-id: pass" line per lesson)
# 4. build and check the HTML
python3 $SK/markdown-textbook-html/scripts/build_html.py $CH -o output/09-sliding-window.html --chapter 09 --title "Sliding Window" --validation stamp.json
python3 $SK/dsa-curriculum-auditor/scripts/audit_html.py output/09-sliding-window.html --manuscripts $CH --smoke
node    $SK/dsa-curriculum-auditor/scripts/render_check.mjs output/09-sliding-window.html shots/
```

## What is verified, and what is not

Verified in this sandbox: the Sliding Window chapter (orientation, 9 lessons, 1 combination lesson, unlocked-combinations and review sections, 45 exercises) passes the manuscript audit against the real chapter-09 spec with zero errors except the human-review gate, which is deliberately left open. Every Java block compiles and every solution block runs with assertions on JDK 21; the combination-lesson solutions and several others are also cross-checked against brute force on thousands of random inputs. The built HTML passes the HTML audit and the jsdom interaction test, and passes the Chromium render check at desktop and phone widths (no horizontal scroll, readable text, tap targets, notes and progress surviving a reload).

Not verified: Java 25 or 27 (the sandbox JDK is 21; the stamp records the JDK actually used); any person's judgment of how well the lessons teach (`review-log.md` is empty on purpose); printing; real phones as opposed to an emulated phone viewport; the other 41 chapters, which are not written yet.
